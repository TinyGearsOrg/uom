# AGENTS.md

Operating rules for AI coding agents working in this repository: uom, a JSR-385 (unit-api 2.2) implementation in Java
with the modules `uom-engine`, `uom` (the native API), `uom-jsr` (the JSR-385 implementation), `uom-codegen` (internal
generator), `uom-tck` and `uom-examples`. Claude Code loads
this file through `CLAUDE.md`, a symbolic link to it; other agents read it directly.

This is the short, must-follow contract. The commands and the reasons behind the rules are in
[CONTRIBUTING.md](CONTRIBUTING.md), the design and its decisions in [docs/DESIGN.md](docs/DESIGN.md). If a rule here
conflicts with an explicit request from the user, ask before overriding it.

## Non-negotiables

- **Every new `.java` file starts with the license header of `config/license-header.txt`**: `spotless:apply`
  writes it, except in `package-info.java` and `module-info.java`, where you copy it; scripts carry
  `# SPDX-License-Identifier: Apache-2.0` after the shebang (`LicenseHeaderTest` checks the Java files).
- **Format with `mvn -q -B spotless:apply`** before you finish; `mvn verify` fails on unformatted code. Do not
  reformat code you do not otherwise change, and do not hand-format against the profile.
- **Never edit generated files by hand**: the Java files whose license header is followed by
  `// Generated by uom-codegen from ...; do not edit.` (the quantity types in `uom-jsr/.../jsr/quantity` and `uom/.../uom/quantity`, the catalogs in
  `uom-jsr/.../jsr/systems` and `uom/.../uom/systems`) and
  `docs/UNITS.md`. Change `data/` or the generator, then regenerate
  (`mvn -q -B -Pgenerate -pl uom-codegen -am process-classes`) and commit the output with the change.
- **A change with no matching test update is incomplete**, unless it has no testable surface (docs only, build
  configuration); say so explicitly rather than skipping silently. A bug fix comes with a test that fails without the
  fix. Tests assert exact values, not just "not null" or "contains".
- **`mvn -q -B clean verify` passes before you report a change as done.** Report failures with their output.
- **Never commit unless the user asks**, never push or open a pull request unless asked, and stage only the files you
  changed (`git add <path>`).

## Pinned outputs to keep in step

- The public API is pinned by `ApiSurfaceTest`. A deliberate API change rewrites `docs/api/public-api.txt` with
  `mvn -B verify -Duom.writeApi`; review the diff, it is part of the change ([docs/DESIGN.md](docs/DESIGN.md), section 8).
- The `java`, `units` and `units-error` blocks of the user documents run in `DocsSnippetsTest` (the list is in that
  test); a `// prints:` comment is the expected output. A `java` block uses `uom`, a `java jsr` block `uom-jsr`; a
  `units` block loads with both. Keep them true when behaviour changes.
- The output of `uom-examples` is pinned twice: `ExamplesTest` and `scripts/consumer/expected-output.txt`, which
  `scripts/verify-release.sh` compares. Update both.
- The README status paragraph states the test counts per module; update them when they change.

## Workflow and code quality

- Read files in full before wide-ranging changes, before editing files you have not inspected, and when
  investigating. Do not rely on search snippets.
- The baseline is Java 17 (`maven.compiler.release`): no APIs or language features of later releases.
- The only runtime dependency is `javax.measure:unit-api`; do not add another.
- The build compiles with `-Xlint:all -Werror`: fix a warning, or suppress it on the smallest element with a comment
  that says why.
- Keep code comments short (1 to 3 lines): state only the non-obvious constraint or rationale, never narrate what the
  code does. Do not recount what a line used to do; the history belongs in the commit message.
- Ask before removing functionality or code that appears intentional. Nothing is released yet, so backward
  compatibility is not required unless the user asks for it; from 1.0, semantic versioning applies
  ([docs/DESIGN.md](docs/DESIGN.md), section 8).
- A design decision gets a decision record in [docs/DESIGN.md](docs/DESIGN.md) section 9 (`DR-nn`: decision, why,
  rejected, revisit if). [docs/TODO.md](docs/TODO.md) lists open work only: remove an item when it is done.
- Run the hooks of `.pre-commit-config.yaml` before you finish: `prek run --all-files` (or `pre-commit run
  --all-files`); they fix whitespace, format, regenerate and check the scripts, POMs and workflows
  ([CONTRIBUTING.md](CONTRIBUTING.md)).
- Documentation is concise and technical, and every statement must match the code and the commands. Check a claim
  (run it, read the code) before writing it down.

## Conventions

- Commit subjects use a conventional-commit prefix: `feat:`, `fix:`, `perf:`, `refactor:`, `chore:`, `docs:`,
  `test:`, `style:`, `build:`, or `ci:` (`scripts/check-commit-msg.sh` checks it).
- Keep the commit body short: state what changed and why, not a walkthrough of how you got there or what an earlier
  draft did.
- No emojis in commits, pull requests, issues, or code. Keep prose concise, direct, and technical, with no cheerful
  filler.
- Answer a user's question before making edits or running implementation commands.
- When responding to feedback or an analysis, say whether you agree or disagree before describing what you changed.

## Git

Multiple sessions may be running in this working tree at the same time, each modifying different files. Git
operations that touch unstaged, staged, or untracked files outside your own changes will stomp on other sessions'
work. Follow these rules:

Committing:

- Only commit files you changed in this session.
- Stage explicit paths (`git add <path1> <path2>`); never `git add -A` / `git add .`.
- Before committing, run `git status` and verify you are only staging your files.

Never run (destroys other agents' work or bypasses checks):

- `git reset --hard`, `git checkout .`, `git clean -fd`, `git stash`, `git add -A`, `git add .`,
  `git commit --no-verify`.

If rebase conflicts occur:

- Resolve conflicts only in files you modified.
- If a conflict is in a file you did not modify, abort and ask the user.
- Never force push.
